# music-dedup

音乐文件去重 Web 工具（Docker 部署，适配树莓派 / NAS）。

不只看文件名 —— 会读音频元数据（时长、码率、采样率、声道、位深），
所以能识别「同名但其实是不同录音」的情况，避免误删。

## 功能

- **相似文件名分组**：归一化文件名后聚类，组内按音质排序，标记建议保留/删除
- **哈希去重**：文件大小相同再算 MD5，内容完全一致的文件归为一组
- **时长一致性校验**：同名但长度差很多的（如 3 分钟单曲 vs 7 分钟现场加长版）
  会在组头标注「时长差 Ns」，且这类文件**默认不勾选删除**
- **低码率清理**：把没有重复副本的劣质文件单独列成一组，方便集中清理
- **批量命名规范**：一键把保留文件改成「歌手 - 标题」，去掉码率/平台/版本噪声
- **安全删除**：删除的文件先移入 `.trash` 回收目录，确认无误后手动清空
- **扫描存档**：结果按「目录+阈值」存档，下次可直接加载，免重新扫描

## 可配置规则

界面左侧「过滤规则配置」共 18 项，分四组，全部带说明文字：

### 基础

| 规则 | 默认 | 说明 |
|---|---|---|
| 相似度阈值 | 0.85 | 文件名相似到什么程度归为一组 |
| 现场版处理 | 避开现场版 | `避开现场版` / `只看音质` / `优先现场版` 三档 |
| 哈希去重 | 开 | 对同样大小的文件算 MD5，找出内容完全一致的文件 |
| 默认勾选建议删除项 | 开 | 扫描后自动预选非推荐版本 |
| 忽略码率标记 | 开 | 比较时去掉 320k / FLAC / 无损 等 |
| 忽略平台水印 | 开 | 去掉网易云 / QQ音乐 / 酷狗 等平台后缀 |
| 忽略版本标记 | 开 | 去掉 live / remix / 伴奏 / 重制版 等版本词 |
| 忽略大小写 | 开 | Hello 与 hello 视为同一个 |
| 宽松匹配 | 关 | 取消「首字符相同」的快速预筛 |

### 匹配

| 规则 | 默认 | 说明 |
|---|---|---|
| 相似度算法 | 字符序列 | `字符序列` / `词集合` / `混合`。词序不同的命名用「词集合」更准 |
| 跨格式匹配 | 开 | 让 `晴天.flac` 与 `晴天.wav` 参与同组比对；关闭则各格式独立成组 |
| 识别版本修饰 | 开 | 把「晴天」「晴天 加长版」「晴天 重制版」视为同一首 |
| 时长一致性校验 | 开 | 读真实时长，比较组内成员是否长度相近 |
| 时长容差 | 3 秒 | 最长与最短差多少秒内算同一版本 |
| 时长差异处理 | 仅提示 | `仅提示` / `拆成两组` / `降权保留` |

### 保留

| 规则 | 默认 | 说明 |
|---|---|---|
| 无损优先 | 开 | 同等条件下优先保留 FLAC/WAV/APE，而非码率更高的有损文件 |
| 等价时保留哪份 | 路径最短 | 音质完全相同时，用 `路径最短` / `路径最长` / `最近修改` / `不区分` 决定 |

### 清理

| 规则 | 默认 | 说明 |
|---|---|---|
| 低码率清理阈值 | 关闭 | 设为 96~320 之间的值，把低于该码率的孤立文件列成一组 |
| 按规范重命名 | 关 | 生成重命名建议，确认后一键应用 |

## 使用

```bash
# 方式一：docker compose（修改 volumes 中的音乐目录路径）
docker compose up -d --build

# 方式二：直接使用 CI 构建的镜像
docker run -d --name music-dedup \
  -p 8321:8321 \
  -v /你的音乐目录:/music \
  -v ./data:/app/data \
  ghcr.io/zeng-qh/music-dedup:latest
```

浏览器访问 `http://<主机IP>:8321`。

`/app/data` 用于存放扫描存档，不挂载也能跑（只是重启后丢失历史）。

## 环境变量

| 变量 | 默认值 | 说明 |
|---|---|---|
| `MUSIC_ROOT` | `/music` | 容器内音乐目录 |
| `DATA_DIR` | `/app/data` | 扫描存档目录 |

## 设计说明

**为什么读音频元数据**：纯文件名匹配无法区分「同一首歌的不同副本」与
「同名的不同录音」。例如 `晴天.flac`（3:30）和 `晴天 现场加长版.mp3`（7:05）
文件名很像，但根本不是同一个东西——删掉就是永久丢失。读取真实时长后可以识别这类风险，
默认不对它们预选删除。

**为什么分桶粗筛**：全量两两比对是 O(n²)，1400 个文件就会 OOM。
先按归一化名分桶（O(n)），只对「长度相近 + 首字符相同」的候选对做精确计算，
配合并查集合并，1422 个文件扫描约 1 秒、内存 35MB 左右。

**为什么删除进回收目录**：判重总有主观成分，直接 `unlink` 风险太高。
移入 `.trash` 后文件名冲突自动加序号，用户可以通过文件管理器恢复。
